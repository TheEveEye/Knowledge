# Voice Recall

**Start voice recall** appears below **Start Recall**. Voice sessions resume through the voice screen; **Continue in text** opens the same saved session.

## One paced tutor turn

Recall uses `gpt-realtime-2.1-mini` over WebRTC for speech, original-audio turn routing and requested tutoring. Completed answers are saved verbatim, then assessed by the session's selected Recall text model through the existing strict Responses structured-output path. This is the sole answer assessor, not a second check of a voice-model grade. It receives the current verified task, rubric, source evidence, learner transcripts, confirmed repairs and assistance timing. It does not hear raw audio; transcription uncertainty must use clarification or the existing repair flow. Subject voice chat retains its separate GPT-Live integration.

Recall capture, playback and the ordered `oai-events` data channel use native WebRTC (`NativeRecallAudio`), with `stasel/WebRTC` pinned to 157.0.0 in Swift Package Manager. This community binary distribution builds upstream WebRTC sources. Recall no longer creates a hidden WebKit audio view or runs its JavaScript transport. Subject GPT-Live chat retains WebKit; the server's Recall HTML remains available for older clients.

The flow is **question → learner answer → silent routing → saved answer → strict assessment → server-controlled feedback → matching UI and speech**. The voice tool `assess_answer` contains only input IDs and an optional structured-control value; it cannot grade, select follow-ups or report disclosures. Explicit text submissions and retries of saved pending assessments bypass the voice router. The native view accepts the result before speech is requested. Delivery receives exactly one user text input containing the approved utterance, with a separate reading instruction and no tools, prior conversation or sample verdicts. This follows the [Realtime text-to-speech workflow](https://developers.openai.com/api/docs/guides/custom-voices). Generated speech transcripts remain diagnostic captions; they never independently change the assessment or feedback card. Model speech remains generative, so compilation cannot establish verbatim delivery.

Feedback contains no grading terminology, generic praise or recaps after correct answers. The selected assessor judges each verified criterion with a strict, keyed schema; the server chooses the next step. A substantive partial initial answer always gets the single uncued completion prompt, or a neutral clarification for genuinely ambiguous meaning. Neither feedback nor the prompt introduces missing answer content. Requested hints remain a separate assisted action. An incomplete follow-up, or a clearly wrong initial answer without substantive recalled meaning, receives verified teaching: the full expected answer when all criteria remain unresolved, otherwise the unresolved criteria's verified contextual answers. Disclosures are derived from that actual server-provided content. A model claim that something was taught cannot suppress teaching or bypass the partial-answer follow-up. After substantial teaching, at most one optional application check may follow. Correct answers receive only “Correct.” before advancing.

The backend binds each decision to its captured question, generation, answer index and evidence turns. The Realtime router no longer returns criterion decisions, `missingMeaning`, feedback, `focusQuote` or disclosure reports for an answer. The authoritative assessor uses a strict keyed JSON schema with required statuses, plain-string missing meanings and learner evidence; it has at most two validation attempts through the existing structured-output mechanism. Newly demonstrated meaning belongs to the current answer. Previously met criteria can retain earlier saved evidence, while repairs of the current answer require its corrected text. Saved pending answers survive provider failure, pause and reconnection; a retry reuses the saved turn and cannot create another attempt. A grading failure is never sent back to the voice router for report repair. Private diagnostics retain provider failures and validation details.

Validation checks ownership, current question and session versions, exact criterion coverage, server-bound evidence turns and follow-up limits. Met and partial decisions require exact supporting excerpts from the current transcript, except for previously met criteria preserving their stored evidence. Actual requested knowledge must be demonstrated: a topic definition does not establish a specifically requested analogy or mechanism, and generic thinking does not establish particular functions such as problem-solving and judgment. Equivalent meanings count without exact note wording; an already expressed meaning must not be challenged merely because the learner used another verb. Structured controls retain deterministic answer-key checks. A conflicting result becomes uncertain and records no learning penalty. Accepted assessments identify the selected text model, `assessmentProvider: selected_text` and `voiceAssessmentVersion: selected-text-v1`.

## Microphone and playback

Recall is turn-based on every audio route. Microphone transmission is gated while the tutor prepares or speaks a turn, while a decision is processed, and while muted, paused or finished. The native transport also waits for the matching output buffer to finish and holds capture for a short output-latency-based tail (250–600 ms) before listening. Manual mode still captures a draft during the learner's turn; it disables automatic submission, not capture.

Raw speech-start events create input candidates only during the learner's turn. The backend ignores tutor-time input and does not interrupt playback in response to detected or transcribed speech. The native transport records speech-start diagnostics without triggering interruption. No transcript matching against tutor wording or custom audio classifier is used.

Capture and playback share the standard WebRTC iOS Voice-Processing I/O device for Apple's built-in echo cancellation, gain control and noise suppression. Audio sources use WebRTC's iOS defaults instead of forcing an additional software noise-suppression pass. The session is configured through `RTCAudioSession` as `playAndRecord` / `voiceChat`, with speaker default and Bluetooth HFP support. Manual audio startup enables the device after remote SDP is accepted. Normal turn changes gate tracks without restarting the device. Stop closes the peer, disables the audio device and balances session activation. No separate audio player or custom audio device handles tutor output.

A floating bottom bar groups microphone mute and pause/resume, with a separate end/restart button. Its options menu contains Repeat question, manual answer mode and Continue in text. These session controls stay out of the question and answer list. Connection, ending and text-continuation progress appear inline in the initiating control.

Provider buffer events describe server stream state and do not prove exact phone playback. The transport accepts playback only for the currently approved utterance, and a playback timeout exposes Retry if completion never arrives.

Session startup waits for accepted remote SDP, the audio-device started callback, the remote audio track, connected peer and open data channel. Before acknowledging an approved turn to the server, the native owner prepares the playback gate for that exact turn. This enables the remote track before speech generation starts, so audio arriving ahead of the data-channel start event does not lose its opening words. Pause, interruption and stale-turn checks still apply. ICE gathering, initial connection and disconnection recovery have bounded deadlines. SDK delegates hand copied event data to the main actor without assuming main-thread delivery.

## Answers, help and navigation

Each audio input is bound to the active question and displayed prompt at speech start. The original transcript is required before assessment is saved; model-written reconstructions never replace it. Noise, greetings, hesitation and transcription failures do not create incorrect attempts. Later discussion after completed feedback is practice without additional independent-review credit.

Input transcription uses `gpt-realtime-whisper` with low delay. Partial transcript events update the existing native answer field while the learner speaks. Fragments are matched by input ID and replace neither another question's draft nor manual edits. The final transcript replaces the partial text; only completed, ended inputs are eligible for automatic assessment or transcript persistence. Finish answer waits for transcription to complete. Partial text is transient and is removed if transcription fails. Semantic turn detection still controls when the learner's answer is ready for a decision.

“Let me think” and “let me finish” establish an explicit thinking hold for the current question. It survives conversational pauses and event-stream reconnects within the live call; new answer fragments remain captured, and no automatic assessment may pass the server hold. The options menu also offers Let me think. “That's my answer”, “I'm done” or Finish answer explicitly releases the hold and submits retained fragments together. Manual answer mode remains a separate preference. Ending the live call clears its hold.

An explicit transcription complaint such as “I said fifteen, not fifty” can propose a repair to one unambiguous span of a pending input or the latest saved spoken text answer. The app displays the original and proposed text for confirmation; the model cannot silently rewrite evidence. Unclear corrections get an answer-free clarification. Knowledge self-corrections remain ordinary answer evidence. Confirmed repairs preserve the original and correction history, including the prior assessment, and never create another answer turn or review. A saved-answer repair reruns assessment within that turn and excludes the episode from memory penalties and independent-recall upgrades, because original audio is not retained to independently verify a post-feedback mishearing claim. Pending-input repairs remain on hold until explicit submission. Older turns, structured-control answers and advanced questions cannot be rewritten through this flow.

Help, explanations and bounded steps, flow and comparison visuals use native views. Support requires exact quotes from the loaded passages for its underlying principle. Examples, analogies, worked scenarios and illustrative numbers may be newly generated; the illustration need not occur in those quotes. The tutor introduces invented details as hypothetical, preserves the principle's qualifications and distinguishes any necessary outside factual knowledge from the notes without claiming external verification. Missing named real-world examples are not invented; the tutor can offer a hypothetical illustration instead. Source membership is validated; semantic grounding remains the tutor's responsibility. No generated HTML or executable UI is accepted. Assistance is recorded before speech dispatch, using utterance timestamps to preserve credit for earlier independent attempts. Neutral clarification and question repetition do not create assistance annotations.

Voice tutoring and regular Recall's Explain more share `recall_tutoringInstructions`. Generated illustrations remain teaching context in the session; they are not added to library notes, question banks, expected answers or grading requirements. A request for an example is help, not an answer attempt. Answer-revealing examples follow the existing assistance/disclosure rules and never establish earlier independent recall. Regular Recall explanations are available after assessment and leave the saved assessment intact.

For a complete correct answer, the backend saves and speaks only “Correct.” and hides the expected-answer recap. Equivalent wording counts; the tutor does not require verbatim notes or unnamed examples. Partial answers stay on the current question for the one useful follow-up. Wrong answers with a clear misconception receive a short targeted correction directly. After substantial teaching, the model may propose one short application or contrast check within the original scope; minor omissions need no check. The server requires newly disclosed criterion content and no simultaneous Recall follow-up. The check is persisted in the current episode, displayed and spoken only after the teaching, and answered through the existing text/voice composer. Its response is saved as assisted `voicePractice`, outside answer turns and assessments. It cannot change criterion completion turns, upgrade the original recall result or create another review. One brief confirmation or correction ends the check and advances; no second check is permitted, including after reconnection.

An isolated “I'm not sure” before an answer receives one small grounded cue without a failed attempt. Continued uncertainty after that cue teaches and moves on. A confidence hedge attached to a substantive answer leaves that answer assessable. Explicit “I don't know” or “explain the answer” requests teach directly, while hints, examples and thinking holds leave room for an answer. Neutral feedback before an uncued follow-up is not recorded as assistance; a hinted prompt is. Answer-revealing help ends a pending retrieval probe. Next and Skip can leave the optional follow-up or check, and Pause/Resume and transcript repair retain their existing behavior. Completed feedback automatically advances through the existing versioned Recall operation after speech finishes; uncertain assessments stay on the current question. The final completion utterance ends the voice call.

For routine corrections the server derives `revealedCriterionIDs` from the verified answer content it actually provides; the voice router cannot claim a disclosure to suppress an uncued follow-up. Requested generative help still identifies the criterion facts it teaches, with source-quote validation. Presenting answer-revealing help closes a pending probe. Support disclosures are recorded before speech dispatch. Existing criterion decisions, initial partial credit and scheduling rules remain intact; later recognition or repetition is assisted, not evidence of earlier independent recall.

**Finish answer** explicitly submits typed, reviewed or structured input. Editing the transcript enables **Finish answers manually**. Explicit help requests still work in manual mode. The answer composer closes after completed feedback, leaving the feedback, help, optional review and navigation controls.

The app owns Next. Common explicit English and German navigation requests bypass model inference, and the Next button uses the same server operation. Other explicit navigation intents can be selected by the silent tutor decision. The next verified question and its evidence are preloaded. The server commits the review before displaying that question, then speaks the displayed question. Next may end an optional follow-up using assessed evidence. Uncertain questions can be skipped without penalty.

## Funding

Voice speech, transcription, turn routing and requested voice help use the server voice allowance. Routine answer assessment and explicit **Review assessment** use the session's selected text provider and model, as text-mode Recall does. Each assessment is accounted for through the existing AI request mechanism; there is no automatic switch of provider or funding after a failure. A spoken challenge must express an explicit review request. Explicit admissions of not knowing teach directly without a grading request.

The provider selection is captured when the session starts; changing account defaults applies to new sessions. Voice Recall does not expose funding labels or diagnostic transcript captions in its UI; the live learner answer transcript remains available in the answer field.

## Lifecycle and diagnostics

The authenticated backend creates the Realtime call, attaches its sideband, executes tools and hangs up the call. Credentials remain server-side. Protocol **5** is required; older clients receive an update-required error. Commands are deduplicated, and durable Recall operations retain version and idempotency checks.

Closing the screen, backgrounding, Knowledge disconnection, audio interruption, headphone disconnection and sign-out stop capture. Calls have a 20-minute limit and end after twelve seconds without an event subscriber. Event-stream reconnection reuses the call; restarting ended audio requires an explicit tap. Pause cancels pending work and playback. Resume recovers a saved pending assessment or repeats the interrupted approved utterance.

Call routing is process-local for the current single-API deployment. Saved attempts and assessments survive API restarts; an interrupted live call must be started again. Legacy persisted queued attempts remain in Recall context for recovery through the saved-session flow.

Starting voice while the account's previous call is already closing reserves the account's opening slot and waits for that shutdown/accounting to finish before creating a new call. An actively running call still requires an explicit stop. Aborted openings do not create a replacement call, and concurrent openings remain blocked.

Realtime response token usage accumulates separately from selected-provider assessment and review usage. Duration is estimated wall-clock time. Raw audio is not persisted. Private learning events record learner transcripts, routing state and tool arguments, the selected assessor's saved judgment, accepted display text and generated tutor transcripts. Standalone admissions such as “I've no clue” are routed to verified teaching before a model can grade or reinterpret them; their original wording and assistance metadata remain in the saved record. A confidence hedge alongside a substantive answer does not activate this shortcut. These records allow comparison of supplied context, decisions, display and speech, but do not prove completed phone playback. Provider retention follows applicable API settings.

Sanitized service logs record validation outcomes, decision duration, display-to-speech request time, server audio-stream start and navigation duration. Credentials and raw provider rejection bodies never appear in those logs; existing private encrypted rejection diagnostics remain available.

Local audio diagnostics use the `dev.kiwiapps.Knowledge` logging subsystem and `VoiceAudio` category. They record requested/supported/active capture processing settings, native audio category/mode, route port types, rates and latency. WebRTC microphone/remote levels and echo-return-loss measurements are included only when exposed by the engine; absent measurements remain null, not zero or evidence of working cancellation. Snapshots occur during capture setup, connection, playback start, detected learner speech, route changes and every two seconds of tutor playback. They contain no raw audio, transcripts, device names/IDs, SDP or network addresses. Diagnostics are observational and never change playback or interruption decisions. A real session on the affected route is required before drawing conclusions about echo suppression.

The app automatically uploads these measurements in bounded batches through its authenticated native client. Uploads are best effort: at most 60 unsent samples are held in memory, no diagnostic upload can block voice commands, and ending voice discards unsent samples. They are never queued on disk or retained across sign-out. Server validation strips unknown fields and maps unrecognized audio category/mode/port strings to `other`; no arbitrary log-file attachment is accepted.

Authenticated API access:

- `POST /api/v1/recall/sessions/:sessionID/voice/:voiceID/diagnostics` accepts `{ batchID, samples }` for an account-owned live/recent call. Batches contain at most 20 samples and are limited to 64 KB. Repeated batch IDs are deduplicated within the file.
- `GET /api/v1/debug/voice-diagnostics` lists the signed-in account's diagnostic files.
- `GET /api/v1/debug/voice-diagnostics/:sessionID/:voiceID` downloads an account-owned JSONL file with `Cache-Control: no-store`, including after voice ends or the API restarts.

Files reside in `${SOURCE_DIRECTORY}/voice-diagnostics/` on the API's private persistent volume, named `<userUUID>_<sessionUUID>_<voiceUUID>.jsonl`. Operations can read them directly over the existing authenticated SSH connection to the API container; no device connection or iPhone log export is required. Each file is capped at 2 MiB. Each account retains its latest 20 files; older files are evicted as new ones arrive. Files expire seven days after the last upload, with cleanup on startup, access and hourly. The directory is private and not served by Caddy. These are technical diagnostics, separate from learner transcripts and grading evidence. The existing source-volume backups also include this directory; normal backup retention applies to those copies.

Native diagnostic samples include `transport: native-webrtc`, callback-derived `audioDeviceRunning`, `speakerEchoGuard` reflecting tutor speech, playback or the capture tail, `automaticInterruption: false`, the app-owned audio category/mode and route, track gates and available audio-level/echo statistics. `microphone_gate` samples record capture enable/disable transitions; `speech_started` records detection without interruption. Older clients may upload the legacy `speech_confirmed` phase. Unsupported measurements remain null. The existing authenticated diagnostic endpoints apply. Native ownership gives explicit routing and lifecycle control; it does not by itself prove effective cancellation on a particular phone or route. See [OpenAI's WebRTC guide](https://developers.openai.com/api/docs/guides/voice-webrtc), [native iOS WebRTC audio](https://webrtc.googlesource.com/src/+/7bca8ca4e2d7833da719c22bc0e1368a1d81ddc9/sdk/objc/native/src/audio/audio_device_ios.h) and the [binary distribution](https://github.com/stasel/WebRTC).

Build and typecheck commands are permitted. Automated tests, harnesses and live voice/device testing are not run without an explicit request. Compilation cannot establish conversation quality, provider access, real latency or audio-route behavior.

API reference: [Realtime client events](https://developers.openai.com/api/reference/resources/realtime/client-events), including manual response creation, response-specific tools and voice activity detection controls. Streaming input configuration follows the [Realtime call reference](https://developers.openai.com/api/reference/resources/realtime/subresources/calls/methods/create) and [GPT-Realtime-Whisper model documentation](https://developers.openai.com/api/docs/models/gpt-realtime-whisper).
