# Knowledge

An iOS 27 SwiftUI app that turns study notes into source-grounded concepts, individual facts, and explained connections using Sign in with ChatGPT. Open `Knowledge.xcodeproj` in Xcode 27, select the shared `Knowledge` scheme, and run on an iPhone or iPad simulator or device. The library remains stored on the device through account switches and sign-out.

This app is unreleased and supports only its current data schema and import checkpoint format. There are no upgrade paths for previous development builds; recreate local development data when the format changes.

## Subject chat

The subject screen keeps search at the bottom left and **Ask about this subject** at the bottom right. **Import notes** is in the top toolbar; **Subject settings** is in the subject menu alongside History and the outline controls. The empty subject still offers a prominent Import notes action.

Subject chat uses the account's default chat model. Its read-only tools browse and search all saved active concepts, facts, connections, topics, contributions, original wordings, review notes, and full original source passages within that subject. Material is retrieved in pages as needed, rather than sending the entire library with every message. Each turn starts from a fresh subject snapshot; unsaved drafts and archived sources are outside this scope. Replies distinguish source evidence from explanation and can cite passages with internal links that open supporting text. Citation links are resolved against the current subject and active source before display. Subject chat cannot edit the library or save learning artifacts yet.

Import review and subject chat share the `ChatOverlay` composer/conversation UI, Markdown and math rendering, and `ChatSession` streaming, queue, retry, stop, and usage-limit handling. `ChatContext` and `ChatTools` supply each screen's instructions, presentation, lifecycle checks, and capabilities; only the import context exposes reversible draft edits. Conversations stay available when the overlay is closed or the subject screen is reopened during the current app session. They are not restored after app termination. Backgrounding pauses active requests for explicit retry, foregrounding resumes queued work, and account changes or subject deletion interrupt affected requests.

## Importing knowledge

Import chat uses the account’s default chat model and a small set of app-executed function tools to inspect import state, search draft entries, read original passages, and apply reversible draft changes. Chat can include or exclude entries, rename draft concepts and new topics, and move new unmerged concepts between existing topics or Unsorted. Inclusion uses the same dependency rules as the review controls; entries with new flagged dependencies require manual review. Chat cannot rewrite facts or evidence, clear review flags, save the import, delete data, or edit the saved library.

Requests submitted during processing wait until the draft is ready for review. The conversation shows queued requests, real response activity, streamed replies, completed edit summaries, Cancel request, Stop, Retry, and Undo. Each batch checks a version from the shared review editor and commits atomically; stale edits are rejected rather than overwriting manual changes. Undo is available for the latest unchanged batch and can work backward through retained batches; later manual edits disable an obsolete undo. Draft edits persist through the existing repository and only enter the library when Save is pressed. Conversations, queued requests, and up to ten undo snapshots are held for the current app session, not restored after termination. Backgrounding stops the active chat request with an explicit retry; queued requests resume in the foreground. Account and permission changes cancel pending chat work. Tool/model/plan rejection and network failures leave completed edits intact and show a retryable error.

While a response is running, Stop replaces Send/X in the existing composer action button and preserves any unsent text. Usage-limit errors include a Manage ChatGPT usage link and pause queued chat requests until an explicit retry. Response parsing retains finalized stream items for tool continuations, accepts confirmed completed JSON responses, and extracts structured error codes from streamed and JSON error envelopes. Finalized items alone never authorize tool execution without confirmed response completion.

Create a subject, such as **AP Psychology**, then choose **Import notes**. V1 accepts searchable PDFs, TXT/Markdown files, and pasted text (up to 25 MB and 300,000 text characters). PDFKit extracts selectable text locally; unreadable or locked PDFs and pages needing OCR produce actionable errors. Imported bytes are copied into Application Support, and passage IDs retain page and section references.

Multiple imports and source rechecks can run at the same time, including imports into the same subject. Each import owns its task, progress, checkpoint callbacks, model selection, pause/resume controls, and background-processing session. Pausing or deleting one draft leaves other imports running; deleting a subject stops only its imports. Account or plan-permission changes pause all active imports. Requests retain the existing batch concurrency policy and share the same account/client. Version-aware reconciliation and serialized saves per subject continue to handle overlapping library updates.

Extraction uses strict Structured Outputs in bounded passage chunks. Concepts and facts carry checked source quotations. Connections reference validated supporting facts and inherit their evidence, avoiding conflicting copies of the same citations. A second pass reconciles compatible repeated concepts, proposes merges with existing concepts in the same subject, and suggests explained connections using supplied facts. Ambiguous internal matches remain separate. Competing theories and qualifications retain their status; source material cannot change the extraction instructions.

The progress screen has a compact header with a readable document title, a plain-language stage, and one progress indicator. A document overview appears immediately from the prepared source, before any model response. It uses recognized headings in document order, or up to six page ranges or numbered parts when headings are unavailable. The first six sections are visible; further sections expand on demand. Each section shows whether it is waiting, being read or checked, checked, paused, or needs attention or review. Status reflects all batches responsible for that section's passages, excluding overlapping context passages. Up to three distinct concept names appear under each section as complete streamed entries arrive; provisional examples are identified as still being checked, and rejected previews are removed. Cards stay in place with no automatic scrolling, definitions, or facts. Connection previews replace the document overview during discovery and remain available while topics are organized. The completed topic overview leads into grouped review. These waiting-screen previews do not add model requests.

Imported concepts are organized before other unsorted library material. Indeterminate progress sits beside the stage text, including during topic organization; measured progress bars reflect completed work within the current stage. The information button opens Import details for the original title, model, elapsed time, and individual batch activity. Running concept, fact, and connection totals stay out of the progress header; selected totals appear during review. Review opens with collapsed topic groups, example concepts, and review flags, with definitions, facts, editing, and source evidence inside each concept. Connections are also collapsed initially. At accessibility text sizes the summary scrolls with the content. Errors remain visible with access to details. Imports use at most 24 primary passages and approximately 4,000 source characters per batch.

If source facts and coverage validate but connection references fail, one targeted repair request can correct only those references using the returned concepts and facts. It retains the original relationship wording. A separate source-adjudication pass checks repaired suggestions' meaning and direction before clearing their flags. Unsupported suggestions remain excluded in a collapsed diagnostics section and do not require a user decision. Fabricated source quotations and invalid facts cannot enter this repair path. Reconciliation uses schemas constrained to supplied concept and fact IDs within the enum budget; ordinary validation still checks every reference and passage.

Extraction keeps coverage ownership in small batches while supplying surrounding source text in both directions, without assuming an outline or other document format. Each initial request reads approximately 4,000 extra characters on each side. Context passages retain their original IDs and can establish the subject or meaning of a required claim; facts must cite a required passage, together with any context needed to support its interpretation. Unrelated context material is not extracted again.

Coverage includes a structured, nullable `contextRequest` describing any missing source context. A substantive claim needing context remains uncertain, even if the model labels it excluded or has already extracted part of it. Uncertain passages, invalid entries, and passages marked extracted without checked citations enter targeted recovery. Recovery reads only the unresolved scope with approximately 12,000, then 36,000 surrounding characters per side, subject to source boundaries and the complete encoded request budget. It stops when no additional context fits. Intermediate recovery attempts admit resolved passages; the last attempt also retains valid partial entries for review. Each attempt's additions, usage, remaining passage IDs, and expansion position are checkpointed before the next request. Claims that remain unresolved keep their source text and a specific reason in passage review; missing context is never treated as a successful extraction or a structural exclusion.

Coverage records are reconciled to the source's actual passage IDs and citations, so repeated or omitted bookkeeping rows do not discard otherwise valid content. Conflicting dispositions remain uncertain. Extraction schemas constrain coverage IDs to the current batch and evidence IDs to supplied passages while within the enum budget; larger windows use text IDs checked against the exact supplied window. Every quotation and reference is validated, and final coverage requires a checked citation for each extracted passage. This preparation does not relax checks on quotation text, fact references, or concept references.

Reconciliation responses require exactly one keyed decision per batch concept. Malformed decisions receive a bounded retry; unresolved protocol/reference failures leave source content and inclusion unchanged, with a processing note. Accepted internal equivalence links form groups with a stable canonical member, so reciprocal proposals do not create merge cycles or content-review flags. Compatibility is still a model judgment based on the supplied meanings, not a match on names alone. Unknown targets cannot enter the graph. Facts, connections and tracked review dependencies are remapped together.

Before naming and topic organization, a separate source-adjudication pass evaluates remaining content issues and checks passages cited only by concepts for missing individual facts. It supplies current entries, dependent entries, original source quotations, and a source window in both directions. Up to four issues share a bounded request; missing context permits one wider reread. Structured outcomes are supported, repair, or human review needed. Valid repairs can correct affected names, aliases, explanations, facts and connection endpoints/types, or recover missing facts attached to supplied concepts. Every quote must match the exact supplied source window, repaired references must remain valid, and manually edited wording is protected. Concept functions and associated processes are not aliases. This is extraction-fidelity review, not external scientific fact-checking.

Review issues have stable IDs and explicit dependent entries. Resolving or acknowledging one issue clears only its inherited blockers; independent issues stay active. Automatic source verification can restore entries deselected for that issue once their remaining blockers are gone, while explicit user exclusions and inferred-connection defaults are preserved. Manual acknowledgement preserves current inclusion choices. Assessment outcomes, exact evidence, model, timestamps, field changes and recovered fact IDs remain in the draft's source-review audit. Each completed request and its remaining work are checkpointed; cancellation, authentication and persistence failures stop processing safely. Invalid or unavailable assessments leave an honest human-review issue. Structural coverage is separate from substantive claims, so a label can remain excluded as independent material while serving as contextual evidence.

Source review uses an issue-specific response schema: only passage issues can assess passage coverage, and repairs are keyed by the permitted entry and field. It assesses structural meaning across source formats without relying on outline markers. Invalid responses receive precise feedback and up to two correction requests before requiring review. Failed assessments are reconsidered after related wording, evidence or facts change, with at most two reassessments per explicit recheck to bound repeated work. Retry counts and a bounded history of rejected responses, validation errors and supplied passage/entry IDs are saved with the draft. Rechecking resets retry budgets while retaining that history.

The review screen groups inherited warnings under their root issues. Optional naming/topic suggestions, discarded connection diagnostics, and source-review audit details have separate sections. **Recheck with source** runs adjudication on an existing review draft without restarting extraction; earlier selection choices without recorded provenance are conservatively preserved.

During connection discovery, the waiting screen shows up to three ideas currently being explored and connection previews from completed reconciliation batches. Suggestions are labeled separately from source-derived connections, and entries with review flags, flagged supporting facts, missing endpoints, or identical displayed endpoints are omitted from this preview. Up to six cards appear initially, with the rest available through a disclosure group. Progress restores these previews from checkpointed results after reopening. There are no extra model requests, speculative streamed connections, or automatic scrolling.

The editable review shows selected counts, supporting passages, original wording for edits, proposed merges, inferred connections, and excluded or uncertain passages. Source-derived entries are selected by default; inferred connections and review flags require user selection. Selecting a connection includes its supporting concepts and facts. Excluding a concept excludes dependent entries. Saving integrates the selected records and supported updates with the latest subject in one transaction and is idempotent for the same draft. Changes to protected wording or organization require a specific choice before any part of the import is committed. A matching quotation establishes provenance, not scientific correctness: the user still reviews the material.

Extraction and reconciliation share a source-fidelity policy: faithful claims are accepted even when the notes are simplified or omit mechanisms, limitations, qualifications, or supporting studies. Review flags are reserved for ambiguous interpretation or identity, unsupported additions or strengthened wording, contradictions in supplied material, and invalid or missing evidence. Existing uncertainty, conditions, quantities, and theory status must be preserved. These stages do not fact-check source claims against outside knowledge or invent missing qualifications.

After reconciliation, ambiguous concepts and concepts with flagged facts receive a bounded AI naming/classification pass. It first supplies cited passages and neighboring context, then permits explicitly unverified general-knowledge suggestions. It cannot rewrite facts, explanations, evidence, connections, merge targets, or inclusion decisions. Note-context suggestions require matching original quotations containing the proposed wording; these checks establish provenance, not correctness or the author's intended meaning. No external lookup is performed and suggestions cannot claim external verification. Ambiguous or unsupported interpretations stay unresolved. Review offers Apply, Undo, and Dismiss while retaining original wording and review flags. Accepted classifications remain browsing suggestions rather than automatic topic assignments. Accepted suggestions and their model, rationale, basis, and source context survive saving; the library displays this provenance and can undo the suggestion while preserving later edits and existing merged concept names. Later reconciliation requests receive the naming provenance so an inferred name is not treated as independent evidence for a merge or connection.

Resolution progress and request usage are checkpointed after each group of up to four concepts. Pause/resume reuses completed groups, and optional suggestion failures retain the original entries with an import note. Drafts without applicable entries make no additional requests.

Completed chunks and reconciliation progress are checkpointed in SwiftData. User-started imports request iOS continued processing runtime and keep running when Knowledge is backgrounded or the screen locks. iOS provides a system Live Activity showing the current stage and overall progress, with a cancellation control. Progress advances from checked batches through connections, naming, and topic organization; completion means the review draft has been saved. Background runtime remains subject to system availability and resource limits. If admission fails, the import continues in the foreground with a notice and pauses safely on backgrounding. System expiration or cancellation preserves checkpoints and requires an explicit Resume. Pausing or changing the ChatGPT connection also stops processing and preserves the draft. Resume explicitly with the selected account and model; completed requests are reused. Model choices come from the active account's catalog. ChatGPT account settings save independent import and chat defaults per registration, initially using the first visible model. New imports start with the import default; choosing another model in an import does not replace either default. New chat messages and explicit retries use the chat default; running requests retain their chosen model. Account settings also grant plan permission and manage usage.

The import and review screens use SwiftUI’s native back button and swipe-back navigation. Going back keeps the draft while active processing continues. Review edits autosave and are flushed when leaving the view. A completed back navigation from a newly created import also closes its creation sheet. Discard Draft is available in a separate Draft actions toolbar menu and asks for confirmation before deleting the draft. No UIKit gesture bridge is used for import navigation. Knowledge keeps the screen awake while any import is running in the foreground, including when its progress screen is closed. Normal auto-lock resumes when the last running import finishes, pauses, fails, or is discarded. The phone can still be locked manually. Each Pause button stops only its import and ends its system Live Activity; activities show the source title to distinguish simultaneous imports. Entering the background keeps admitted imports running and safely pauses imports without background runtime; library saves and undo operations still pause when backgrounded. Discarding stops that import and removes the draft and its unshared source copy.

Concepts, facts, and connections have stable UUIDs. Connections can be browsed from either endpoint, supporting shared functions such as several concepts contributing to attention. Question generation, scheduling, OCR/images, Office files, cloud sync, and a visual graph are future features.

Concepts are organized into a subject-wide topic outline during import, after extraction and reconciliation and before review. The import uses its selected ChatGPT model to prepare at most three topic levels from concept summaries and source headings, then assign batches of up to 25 concepts concurrently. Every pending assignment batch is submitted without an app-imposed concurrency cap, matching initial reading batches. The resolved outline, stable topic IDs, and proposed updates are checkpointed before assignments begin. One coordinator combines validated results as requests finish, preserves candidate order, and saves each batch before displaying progress, including concepts left Unsorted. Pause, cancellation, or a request/storage failure stops outstanding workers; saved batches remain reusable. Pause/resume and reopening restore the saved count and topic overview, reuse the outline, and request only unfinished concepts, even when earlier batches finished out of order. Interrupted requests in unfinished batches may repeat. Once grouping finishes, the completed plan is checkpointed with the draft. Topics are browsing headings and do not change source-grounded concepts, facts, or knowledge connections.

The library displays the saved hierarchy immediately; opening a subject does not start model requests. Topic paths are visible during review. Saving commits the selected concepts, facts, connections, topics, and placements together, resolves accepted combinations, and omits new branches used only by deselected concepts. Existing assignments are preserved unless an explicit supported update changes them; locked placements and edited fields require approval. Concepts without a placement and unlocked Unsorted concepts can be grouped during a future import.

The library shows collapsible topics with descendant concept counts and remembers expanded branches per subject. Search includes aliases and topic paths. Uncertain placements remain visible under Unsorted. The subject menu expands or collapses the topic tree and opens History. Long-press a topic to rename it. Move a concept from its detail screen, context menu, or leading swipe; manual moves lock its placement until unlocked.

## Saving overlapping drafts and history

Each new draft keeps an immutable subject base, reused by extraction, reconciliation, organization, and resume. Reconciliation and organization may propose supported updates to existing entries, alongside additions. Original extracted wordings, quotations, selections, rejected suggestions, and passage acknowledgements remain available independently of canonical library wording.

Save shows **Updating your subject…**. If nothing relevant changed since preparation, it applies the prepared changes without another model request. Otherwise compatible additions and independent field changes combine locally. Only affected groups with potential semantic overlap go to the selected model. Topic matching considers contained concepts and parent context, rather than names alone. Equivalent identities are resolved as groups before remapping facts, connections, topics, placements, and contributions. Uncertain matches stay separate; contradictory sourced claims retain their wording, conditions, and attribution. There is no external fact-checking or unrelated library cleanup.

A proposed replacement of edited wording or locked organization opens **Review changes**, with the affected item, the reason, sources, and relevant choices. Related identity combinations appear as one decision. Choices are saved before the import can proceed. The entire import remains uncommitted until consequential decisions are resolved. Supported AI suggestions cannot write directly to the database; references, quotations, topic structure, protected fields, and the exclusion of unselected entries are validated first.

Subject updates use immutable entity versions and revision manifests alongside the materialized SwiftData library. Unchanged versions are reused, and source documents are stored independently. Contribution records retain each import's evidence and original wording. Retired identities keep redirects for historical references and older drafts. Manual changes to wording, topic organization, placement locks, and saved naming suggestions go through the same revision writer. Field ownership is tracked individually.

Import saves and undo operations are serialized per subject. A final subject-revision and draft-version check, materialization, evidence contributions, history record, and saved-job status share one synchronous database save. No model request runs inside that transaction. Immutable merge preparation, model-response application, checkpoint encoding, and commit serialization run off the UI actor. Concurrent subject changes trigger another reconciliation against the latest subject; unchanged decisions are retained. After three continuing changes, the draft keeps progress and offers Retry. Closing the import screen keeps foreground work alive; account changes, cancellation, backgrounding, and request failures leave the draft and saved library intact.

**History** lists imports, manual changes, and undo operations with source titles, dates, brief summaries, before/after details, and evidence on demand. **Undo import** is available for saved imports. Undo builds an inverse from the changes actually committed, preserves later edits, later source contributions, and dependent entries, and creates a new history entry. It does not restore an old snapshot or delete original source material. Repeated Save and Undo actions are idempotent. Any required undo decision uses the same review flow, with no partially applied changes. Redo, timeline restoration, and undoing manual history entries are outside this implementation.

Subjects require a revision head from creation. The initial revision ID is reserved before insertion and committed with the subject in one transaction; only this root revision has no parent. Each draft requires an immutable base revision, including for topic organization. Permanent subject deletion remains a separate destructive action.

## Current persistence contract

Library persistence accepts current revision records and their original wording, evidence, and prepared-source bytes directly. It no longer constructs temporary draft objects or regenerates original payloads to initialize saved models. Revision summaries are required. History-related model fields are initialized by current constructors, without schema defaults for older stores.

Draft branches retain the base revision, operation ID, optional in-progress merge plan, and a required semantic-results array. Change sets are recomputed from the selected draft and its immutable base; unused branch change sets, explanations, and duplicate base metadata have been removed. Write-only identity maps have also been removed from plans and revisions; canonical references resolve through the redirects in immutable entity records. Branch and pending-undo writes require payloads encoded off the UI actor, and branch writes always check the draft edit version. Identity combinations use group-level protection review.

Topic plans and reconciliation/outline responses require `updates` arrays, using `[]` when there are no proposals. A missing or null array is rejected. There is no fallback from an import's immutable base to a fresh live-library context, no pre-history import UI, and no migration, backfill, or older-draft decoder. Recreate local development data from earlier formats.

The remaining fallbacks and optional values serve current operations or external contracts:

- Checkpoints can lack a combined draft, topic plan, or merge plan while processing is unfinished. Completed batches, pending source repairs, semantic results, explicit choices, and pending undo plans preserve interrupted current-format work.
- Retired-identity redirects preserve references from history, contributions, and overlapping drafts. Undo keeps later edits, contributions, and dependencies through the same revision writer.
- Sparse record accessors handle fields belonging to different entity kinds. Initial and manual revisions still serialize synchronously; import and undo commits use prepared payloads. Empty-state labels and unreadable-data handling keep current failures understandable and allow damaged drafts to be discarded.
- External model metadata can omit display names and visibility; OAuth/JWT decoding accepts the service's string/list audiences and textual/numeric refresh times. Responses streaming keeps event-name/type, text-delivery, and error-envelope fallbacks. These are external API handling, independent of the local library format.

## ChatGPT sign-in

The app uses OpenAI’s dynamic registration flow for local, personal, and open-source apps. It needs no API key, client secret, or pre-issued partner client ID. Identity sign-in and permission to use a ChatGPT plan are separate: declining the optional plan permission still lets the user sign in.

The sign-in screen offers **Continue with ChatGPT** and saved account registrations. Account settings support switching accounts, adding a registration, granting plan permission later, opening ChatGPT usage settings, and signing out. Each registration has a stable label, so accounts with the same email remain distinguishable. The first connection with plan permission shows a dismissible welcome message.

The authentication layer:

- Generates a stable installation host ID and fresh state, nonce, and PKCE values for every authorization attempt.
- Receives the issued client ID on a temporary `http://127.0.0.1:<port>/auth/callback` listener. It retains the registration before token exchange so a later attempt can reuse it.
- Exchanges the code using the issued client ID and verifies ID-token signature, issuer, audience, expiry, and nonce using OpenAI discovery/JWKS and JWTKit 5.
- Stores each registration and its credentials separately in the Keychain, available after the first device unlock following a restart so active imports can securely persist rotating refresh tokens while the screen is locked. Credentials remain device-only and do not sync or enter SwiftData or UserDefaults. Starting an import saves the active account while foregrounded to apply this protection before background processing begins.
- Restores the selected account, serializes refreshes, saves rotating refresh tokens, and attempts remote revocation before clearing the selected account’s local credentials on sign-out.

The plan request client supports model discovery, task-specific instructions, strict JSON schemas, and streaming Responses API requests for concept import. It uses the active account’s refreshed OAuth access token, `GET https://api.openai.com/v1/models`, and `POST https://api.openai.com/v1/responses` with `store: false`, `stream: true`, and array input. It captures returned token counts and handles admission errors, plan eligibility and usage-limit failures, refusals, incomplete/interrupted responses, and cancellation. Account settings link to ChatGPT’s usage settings.

## Native callback adaptation

OpenAI receives the required HTTP loopback redirect URI. After validating that callback, the local listener redirects the embedded `ASWebAuthenticationSession` browser to the app’s private callback scheme with an unpredictable, attempt-specific marker. The authorization code and tokens are not included in that native bridge URL. This bridge dismisses the browser through Apple’s supported custom-scheme callback mechanism; it does not register a custom redirect URI with OpenAI.

The listener binds to IPv4 loopback, limits request sizes and concurrent connections, validates the request host/path and OAuth state, and accepts one callback per attempt. Cancellation, timeout, or backgrounding closes the browser and listener. No broad ATS exception or Bonjour advertisement is configured.


## Build

JWTKit and its transitive dependencies are resolved through Swift Package Manager.

```sh
xcodebuild build -project Knowledge.xcodeproj -scheme Knowledge -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO
```

This project has no test target or test harnesses. Follow the no-tests policy in `AGENTS.md`.
